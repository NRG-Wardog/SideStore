# Offline onboarding continuation regression

This focused fixture covers the continuation after successful authentication, not another SRP/2FA matrix. It projects unmodified production method bodies for SignInOperation's selected-route wrappers, execute/cancel lifecycle and fetchTeam; AuthManager session acquisition and identity checks; the real TaskChainCoalescer actor; AnisetteProvider selection; DeveloperPortalProxy's bound-session/fetchTeams path; and the remote context's actual cache/revocation behavior.

Only external boundaries and surrounding app/UI/database orchestration are synthetic. Apple authentication produces an in-memory accepted response; portal calls only record the selected session's synthetic route. No credentials, HTTP, remote provider, native ADI or persistent store is used. Finalization's wrapper is real; certificate work is replaced by a read-only fake portal validation through the real bound proxy. Other diagnostic validators remain owned by the existing suites; the additional registration producer/validator projection is described below.

Generate with `python3 -B .ci/iloader-onboarding-scope/generate.py --output-dir OUTPUT --sidesign-root SIDESIGN`. Source checks use the same optional root arguments with `test_source.py`. Generate never compiles or executes Swift. The CI-owned fake fixture compiles exactly CandidateOnboarding.swift, BoundaryDoubles.swift and RuntimeTests.swift, then runs its binary with the case-export JSON path as its sole optional argument. Successful execution emits ILOADER_ONBOARDING_SCOPE_FIXTURE_PASS and exactly eight unique case labels. A process watchdog exits with failure if a broken key partition leaves the queued gates blocked.

Source evidence binds every extracted production declaration, all fixture inputs and the exact three-file output closure. Default provider bytes, cancellation lifecycle and the coalescer implementation are checked against the delivered baseline; the nil/default session key and acquisition order remain unchanged.


## Device-registration diagnostic coverage

The same source-generated fixture also extracts the actual `registerCurrentDevice` method, scalar SideSign observer declarations, operation/portal/parser enums, immutable `pc1` producer and strict validator. In-memory UDID, cellular, device-list and device-register boundaries exercise success, fallback, missing identifier, first-error priority, cancellation, pre-response and post-HTTP-200 local authentication rejection, portal/parser evidence, prior observer forwarding, known wrappers, secret canaries, causal cycles and truncation. The existing 8 onboarding cases remain unchanged. Runtime additionally writes `registration-cases.json` beside `cases.json`, containing 14 named synthetic error observations for the independent service/host wire and Copy Details fixture.

The production calls keep their original order, retry/readiness behavior and portal arguments. The fallback helper `fetchUDID(useStatic:)` internally discards its own live-retry error with `try?`; the registration observer cannot recover that hidden error. It records only the original live error and the actual returned fallback state or thrown fallback error. No complete hidden-internal-causality claim is made.

Registration runs against inert local API boundaries, not live authentication, networking or native Minimuxer. The extracted register method is invoked directly; the original queued-authentication cancellation/identity tests still exercise `fetchTeams`, not a full queued registration pipeline. No physical-device or native-provider evidence is implied. Swift compilation/runtime remains a separate CI gate; Python source/projection checks alone do not establish Swift execution.
